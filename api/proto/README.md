# Dieter schemas

All of Dieter's protobuf schemas live here. They have three audiences:

| Package             | Files                             | Audience                                                                                                                                                                                                                                                                                 |
| ------------------- | --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dieter.v1`         | `dieter/v1/*.proto`               | **The daemon API.** One service per domain (`CardService`, `ConversationService`, `ScreenService`, …) plus `common.proto` for shared types. Every client, including the CLI, uses it locally, over authenticated direct TLS, over the WebRTC data channel, or through the gateway relay. |
| `dieter.gateway.v1` | `dieter/gateway/v1/gateway.proto` | **The gateway API:** accounts, sessions, daemon enrollment and the daemon link.                                                                                                                                                                                                          |
| `dieter.client.v1`  | `dieter/client/v1/client.proto`   | The in-process contract between the Kotlin core and the native UIs (commands, slices). It never crosses the network.                                                                                                                                                                     |
| `dieter.core.v1`    | `dieter/core/v1/*.proto`          | The Kotlin core's on-device records.                                                                                                                                                                                                                                                     |

There is no parallel REST API, JSON view model, SSE event format, or web client.

`GetConversation` returns a bounded lightweight tail. Tool inputs and outputs
are represented by previews, byte sizes, and a payload revision; clients fetch
the full value with `GetToolOutput` only when it becomes visible. Native clients
use `WatchConversation` with `after_seq` resume semantics.

## Changing a schema

Edit the `.proto` files, then regenerate from the repository root:

```sh
just generate
```

That runs `buf lint` and `buf generate` with the templates in `api/`:

| Template                                          | Output                                                                                                                           |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `buf.gen.go.yaml`                                 | Go messages and gRPC stubs in `internal/gen`                                                                                     |
| `buf.gen.connect.yaml`                            | Connect handlers for `dieter.v1` (`simple` signatures)                                                                           |
| `buf.gen.swift.yaml`, `buf.gen.swift-client.yaml` | Swift messages and gRPC clients in `apps/apple/DieterKit` (macOS only; the plugins are built from DieterKit's resolved packages) |

Kotlin is generated by Wire during the Gradle build straight from this
directory; nothing is committed. Generated Go and Swift code is committed so a
fresh clone builds without protobuf tooling, and CI fails when it drifts.

`buf lint` uses the STANDARD rules except the request/response naming and enum
prefix rules that the API predates (see `buf.yaml`). `buf breaking` covers
`dieter.v1` and `dieter.gateway.v1`. Dieter ships one version across gateway,
daemon and clients: a breaking change is allowed only together with raised
minimum client and daemon versions in `deploy/gateway/compatibility-policy.json`.
